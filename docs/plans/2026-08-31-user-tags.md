# User Tags — Program design

> 작성 시점 정직 고지: 이 문서는 구현과 **같은 작업 단위**에서 작성됐다. 구현 전 승인된
> 설계서가 아니라, 게이트가 요구하는 "코드의 형태"를 리뷰 가능하게 남긴 기록이다.
> 설계 결정 자체는 구현 착수 전에 내렸고, 기각된 대안도 그대로 남긴다.

## 문제

라벨링 축 5개 중 4개가 자동 생성이고, 자동 생성이 아닌 축이 없다.

| 축 | 생성 주체 | 사용자 지정 |
|---|---|---|
| `scope_type` | 추출 시 판단 | ✗ (2종 고정) |
| `category` | 추출 시 판단 | ✗ (5종 고정) |
| `coding_agent` | 실행 환경 | ✗ |
| 온톨로지 `domain/category` | 분류기 생성 | ✗ |

스키마에는 자유도가 있으나 **접근 표면이 0개**였다 — MCP 도구 9개 전부 `readOnlyHint: true`, CLI 6개 명령 전부 읽기/인덱싱, `ui/server.cjs` 에 쓰기 엔드포인트 없음. `insertFact`/`updateFact` 호출자는 `fact-extractor.ts` 와 `consolidator.ts` 뿐이다. 유일한 사용자 경로가 `sqlite3` 직접 조작.

## 설계 결정

**저장 형태: `facts.tags TEXT` (JSON 배열)** — 기존 `source_exchange_ids` 와 동일 패턴.

기각한 대안: 정규화 `fact_tags(fact_id, tag)` 테이블. 조회는 빠르지만 마이그레이션·조인· 삭제 정합성이 붙고, 활성 fact 23.5k 규모에서 `LIKE` 스캔이 수십 ms라 이득이 비용을 넘지 않는다. 태그 수가 커지면 그때 승격한다(컬럼은 유지한 채 인덱스 테이블 추가 가능).

**자동 파이프라인은 이 컬럼을 쓰지 않는다** — 불변식. 태그가 통합·재분류·재임베딩을 통과해 살아남는 근거이자, 사용자가 태그를 신뢰할 수 있는 유일한 이유.

**정규화는 쓰기 시점 1회** — trim → 공백을 `-` 로 → 소문자. 읽기 시점 정규화는 LIKE 매칭과 어긋나므로 금지.

**부분 적용 금지** — 태그 N개 중 하나라도 무효면 전체 거부. 일부만 반영되면 사용자가 무엇이 들어갔는지 알 수 없다.

**LIKE 패턴에 JSON 따옴표 포함** — `tags LIKE '%"' || ? || '"%'`. 없으면 `api` 가 `api-v2` 를 잡는다. 회귀 테스트로 고정(결함 주입 시 실제 FAIL 확인).

## 타입 · 시그니처

```ts
// src/types.ts
interface Fact {
  // …기존 필드
  tags?: string[];            // 사용자 지정. 자동 파이프라인 미기록
}

// src/fact-db.ts
export const MAX_TAG_LENGTH = 64;
export const MAX_TAGS_PER_FACT = 32;

export function normalizeTag(raw: string): string | null;
export function parseTags(raw: unknown): string[];

export function getFactTags(db: Database, factId: string): string[];
export function addFactTags(db, factId, rawTags: string[]):
  { tags: string[]; added: string[] };
export function removeFactTags(db, factId, rawTags: string[]):
  { tags: string[]; removed: string[]; absent: string[] };
export function setFactTags(db, factId, rawTags: string[]): string[];

export function listTags(db, opts?: { project?; includeInactive? }):
  Array<{ tag: string; count: number }>;
export function findFactsByTags(db, rawTags: string[],
  opts?: { project?; match?: 'all'|'any'; limit?; includeInactive? }): Fact[];
```

실패 계약: 존재하지 않는 `factId` 는 `fact not found` throw(fail-loud). 무효 태그는 `invalid tag` throw. 상한 초과는 `too many tags` throw. `removeFactTags` 의 미존재 태그만 에러가 아니라 `absent` 로 보고.

## 콜스택

```
CLI  memory-bank tag  ─→ cli/memory-bank.js  ─→ dist/tag-cli.js
     memory-bank tags ─→ (--browse 주입)      ─┘
                                               │
MCP  tag_fact   ─→ mcp-server.ts handler ──────┤
     list_tags  ─→ mcp-server.ts handler ──────┤
     search_facts(tags:) ─→ 메모리 내 필터 ────┤
                                               ▼
                        fact-db.ts  add/remove/set/list/find
                                               │
                                               ▼
                        facts.tags  (UPDATE / SELECT … LIKE)
```

자동 파이프라인(`fact-extractor` → `consolidator` → `ontology-classifier`)은 이 스택에 진입하지 않는다 — 교차점 없음이 곧 불변식.

## 검증

- 신규 20건 포함 **501/501** 통과
- anti-vacuous: LIKE 따옴표 경계를 제거하자 접두어 오매칭 테스트가 FAIL, 복원 시 통과
- 라이브 스키마 스모크 20/20(한글 태그·거부 케이스 6종 포함), 테스트 fact 정리 확인
- CLI 전 경로 실행 확인(add/show/remove/index/find), 가이드 수록 SQL 3종 실 DB 실행 확인
